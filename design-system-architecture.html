00 — Overview

設計方針まとめ
求人マッチングサイト フロントエンド

コンポーネント構造・スタイルの型安全度・文言管理という3つの軸それぞれについて、何を採用し、なぜそれを採用するのかを整理した資料。 判断の根拠まで残すことを目的にしています。

DECISION 軸1 = 単一コンポーネント + DU + Record表
軸2 = as const satisfies
軸3 = Actionカタログ + intent軸 + 辞書運用

#大原則

Principle

コンポーネントは「重複を消す装置」ではなく「変更を閉じ込める装置」。

DRYを目的にすると「似ているか?」という主観の議論になり、意見が割れます。 「一緒に変わるか?」は事実なので、こちらを判断軸にします。 似ている(現在の形が同じ)と、一緒に変わる(将来の運命が同じ)は別物です。

#前提となるサービスの性質

POSのような業務システムと比べたとき、この事業には3つの構造的な違いがあります。これが設計判断に直結します。

観点業務システム求人マッチング影響
利用者単一(店舗スタッフ)二面(求職者 / 企業)語彙が面ごとに変わる
主な操作会計・注文(即時)フォーム・検索・応募バリデーションが桁違いに多い
公開性社内端末公開Webサイトa11y と SEO が実質要件

#4つの軸と、それぞれの器

設計の議論が噛み合わなくなる原因は、性質の違う4つの軸を1つのコンポーネントで同時に扱おうとすることにあります。 軸ごとに別の器を用意すると、判断が単純になります。図の箱をタップすると各セクションに移動します。

01.22つの軸を交差させる

ボタンには性質の違う軸が混ざっています。見た目(intent)と振る舞い(kind)を別々のDUにして、交差型で合成します。9パターンを手で書く必要はありません。

// 軸ごとに制約を宣言するだけで、正しい型が組み上がる

src/lib/components/Button/Button.types.tstypescript
export type ButtonIntent = 'primary' | 'neutral' | 'subtle' | 'destructive';
export type ButtonSize  = 'sm' | 'md' | 'lg';
export type ButtonWidth = 'auto' | 'full';

/** 見た目の軸: disabled を持てるかどうかがここで決まる */
type Appearance =
  | { intent: 'primary';     disabled?: boolean }
  | { intent: 'neutral';     disabled?: never }   // 存在しえない
  | { intent: 'subtle';      disabled?: never }
  | { intent: 'destructive'; disabled?: boolean };

/** 振る舞いの軸: 生成する要素が決まる */
type Behavior =
  | { kind: 'button'; onClick: () => void }
  | { kind: 'submit' }
  | { kind: 'link'; href: string; disabled?: never };

/** 共起制約のない調整パラメータ */
type Common = {
  size?: ButtonSize;
  width?: ButtonWidth;
};

export type ButtonProps = Common & Appearance & Behavior;

なぜ disabled?: never なのか

フィールドを単に省略するだけでは、ユニオン型に対する余剰プロパティチェックが緩く、他のメンバーに存在するプロパティは通ってしまうことがあります。 never と明示すれば確実にエラーになります。

01.5案5へ移行する合図

  
いずれか2つ以上に当てはまったら、シェル + variant分割 + ファサード表への移行を検討します。求人サイトでは応募ボタンが起点になりやすい部分です。

求職者側と企業側で見た目の密度が変わりますが、これを intent で吸収すると組み合わせが爆発します。size / density のトークン軸かテーマ切り替えで扱い、intentを増やす方向に逃げないのが重要です。

02.3satisfies が何をしているか

  
型注釈は「検査」と「上書き」の2つの仕事を同時にやっています。satisfies は検査だけを行い、上書きをしません。


  

    

    
    
// as は「検査せず上書き」、satisfies は「検査して上書きしない」。名前は似ているが性質は正反対

  


  

    
正直な注意

    

      値が単なる string の Record<Intent, string> では、satisfies の利得はほぼゼロです。
      キー型がすでに有限ユニオンなので keyof の結果は変わりません。
      それでも採用するのは、後からトークン表(段階3)へ育てるときに書き換えが不要だからです。
      定数テーブルは最初からこの形にしておいて損がありません。
    

  


  
02.4守れないもの

  

    
◯ 守れる — 構造

      
  • 全intentの実装が存在すること
  • 存在しないキーを書いていないこと
  • 型定義と表が1対1で同期し続けること

    

    
✕ 守れない — 内容

      
  • クラス名のtypo(text-nuetral-900)
  • 存在しない値(bg-red-1000)
  • competing class の衝突

    

  

  
内容側は Tailwind CSS IntelliSense と ESLint に任せます。型で全部やろうとすると、記述量に対して見返りが合いません。


  

    
Tailwind の制約

    

      bg-${color}-600 のような動的組み立ては禁止です。JITはソースを文字列としてスキャンするので、
      完全なクラス名がリテラルとして存在しないとCSSが生成されません。表に完全な文字列を書く方式なら安全です。
    

  


  







  
03 — Axis 3

  
文言・ラベル管理

  
ラベルもvariantも「操作」から導出される従属物です。操作そのものをカタログ化し、そこから見た目と文言を導きます。


  

    ADOPT
    案4 — Actionカタログ + intent軸
+ needsConfirm を intent から分離
  


  
03.1却下した案

  

    
✕ label を文字列ユニオンで制約する

    

      { intent: 'destructive'; label: '削除する' | '取り消す' } のような形は採用しません。
      ① 文字列は識別子ではない(「キャンセル」がフォーム離脱にも応募取消にも使われる) /
      ② コピー修正が型定義の修正になる /
      ③ 多言語化で壊れる /
      ④ 本当のバグ(destructiveが青く出る)を防げない。
    

  


  
03.2操作を単一の真実にする

  
呼び出し側は action だけを指定します。intentもlabelも指定できないので、規約が破れません。


  

    

    
    
// label / intent / needsConfirm は不可分にセットなので、操作単位で持つ

  


  
03.3intent と needsConfirm を分離する

  

    業務システムでは「取り返しがつかない = 赤 = 確認が必要」が一致していました。
    求人サイトでは一致しません。ここが前提変更で最も効いた設計要件です。
  

  

    

      
操作取り返しがつかない赤くすべきか理由

      
        
応募するはいいいえ主要CTA。赤は不適切

        
選考を見送るはいいいえ企業側の通常業務。赤は配慮を欠く

        
掲載を終了するはいどちらとも再掲載は可能

        
アカウントを削除するはいはい完全に不可逆

      
    

  

  

    
結論

    
needsConfirm を intent から独立させることで、「赤くはしないが確認は取る」が表現できるようになります。

04.4キー設計のルール

  
キーは意味で作ります。場所や見た目でキーを作ると、移動・変更で意味を失います。

  

    
◯ 意味がキー

      
applyJobrejectApplicantcloseJobPosting

      
操作や概念そのものを指しているので、UIが変わっても生き残る。

    

    
✕ 場所・見た目・汎用

      
detailPageButton1blueButtonTextcommon.cancel

      
common.cancel が特に危険。「フォーム離脱」と「応募取消」を同じエントリにまとめる入口になります。

    

  


  
04.5エラー文言の3層構造

  

    求人サイトはフォームの塊なので、ここが最も効きます。
    ドメイン層はDUを返し、文字列への変換は表示の直前で1回だけ行います。
    こうするとバリデーションのテストが文言に依存しなくなります。
  

  

    
domain/validation-error.ts1. ドメイン


export type ValidationError =
  | { type: 'required';      field: FieldName }
  | { type: 'tooLong';       field: FieldName; max: number }
  | { type: 'invalidFormat'; field: FieldName }
  | { type: 'duplicated';    field: FieldName };
// max を数値のまま保持できるのが文字列との決定的な差

  

  

    
messages/ja.ts2. カタログ


type MessageCatalog = {
  [K in ValidationError['type']]:
    (e: Extract<ValidationError, { type: K }>) => string;
};

export const validationMessages = {
  required: (e) => `${labelOf(e.field)}は必須です`,
  tooLong:  (e) => `${labelOf(e.field)}は${e.max}文字以内で入力してください`,
  invalidFormat: (e) => `${labelOf(e.field)}の形式が正しくありません`,
  duplicated: (e) => `この${labelOf(e.field)}はすでに使われています`,
} as const satisfies MessageCatalog;
// エラーを1種類追加すると、ここがコンパイルエラーになる

  

  

    
ProfileForm.svelte3. 表示


const message = $derived(
  error ? resolveValidationMessage(error) : null
);
// テンプレートは値を投影するだけの薄い層

05 — Roadmap

  
導入順序

  
1〜3は今すぐ着手でき、合計で半日〜1日程度。4はフォームを書き始める前に決めておくと後戻りがありません。タップで進捗を記録できます(ページを閉じるとリセットされます)。


  

    0 / 6
    
  

  
    

  
    05.1今回やらないこと
    
  
    やらない判断も記録しておくと、後から「なぜ入れなかったのか」を再検討できます。
    
  
    
    
    型レベルフィルタ
    KeysWhere のような導出型。intentが4つなら手書きのほうが圧倒的に読みやすい。10種類以上になったら再検討。
    
    
    Brand型 / opaque type
    シェルコンポーネントが存在しないため、そもそも発生しない問題。案5へ移行したときに再検討。
    
    
    label の文字列ユニオン制約
    却下のまま。多言語化とコピー修正で確実に壊れる。
    
    
    全ボタンのカタログ化
    1箇所しか使わない文言まで入れると、辞書を開かないとUIが読めないコードになる。
    
  
    

  
    05.24軸の外で優先度が高いもの
    
  
    ボタン設計より先に効く、または並行して進めるべき項目です。
    
  
    
    
    1. エラーメッセージの3層構造
    最優先。会員登録・プロフィール・職務経歴・求人投稿・応募フォーム。バリデーションの種類が業務システムより一桁多く、表示先も文脈で変わります。
    
    
    2. AsyncBoundary
    検索結果・応募者一覧・スカウト・通知が同じ4状態を持ちます。空状態が事業KPIに直結するため、改善を1箇所に閉じ込める価値が高い。一覧が3画面目に達したら導入。
    
    
    3. DOM構造 / a11y
    公開サイトかつ求人という性質上、実質的な要件。<button>と<a>の使い分け、ラベル紐付け、aria-live、フォーカス順序。ここは主導していい領域。
    
    
    4. 用語集の作成
    実装より先に事業側と語彙を突き合わせる。二面性という論点が最初から存在するため、後から統一するほうが高コストです。
    
  
    

  
    05.3チームで合意を作る
    
  
    
    
    運用の提案
    
    
    
      「変更イベント表」をデザインシステムのREADMEに置き、この変更が来たときどこを触るかを明記します。
      そうすると議論が「どっちが綺麗か」から「このイベントで何ファイル触るか」に移り、数えれば決着がつく状態になります。
