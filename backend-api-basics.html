Chapter 0いま分かっていないのは実は2つだけ

結論から言います。あなたは既に必要なものの8割を持っています。

Lv1〜Lv5 で書いてきたコードを思い出してください。たとえば問9 namesAbove はこういう形でした。

// あなたが書いてきたコード
const products: Product[] = [
    { name: 'ペン', price: 120 },
    { name: 'ノート', price: 300 }
];

const namesAbove = (items: Product[], min: number): string[] =>
    items.filter((p) => p.price > min).map((p) => p.name);

今回やることは、本質的にはこれと同じです。違うのは配列の出どころだけです。

// これからやること
const works = await getWorks();  // ← 配列が「別のコンピュータ」から来る

works.filter(...).map(...)      // ← ここから先は完全に同じ
この資料の核心 新しいのは ①データがどこから来るのか と ②なぜ待つ必要があるのか の2つだけ。 データが手に入った後の加工は、あなたが45問かけて身につけたものがそのまま使えます。

そして②の「待つ」は、あなたのカリキュラムの Lv6（問46〜50）そのものです。つまり今つまずいているのは、能力の問題ではなくまだ習っていないからです。順番として自然です。

あなたが既に持っているもの今回足すもの
.map / .filter / .reduceデータの入手経路（API）
Record 構築・動的キー「待つ」構文（async / await）
判別可能ユニオン・never 網羅コードが動く「場所」の概念
Result 型・fail-loud の発想秘密（API キー）の置き場所
ジェネリクス <T> / keyof—（そのまま使う）

Chapter 12台のコンピュータ

まず一番の基礎から。Web の世界には常に2台以上のコンピュータが登場します。

「バックエンド」とは、この右側で動いているプログラムのことです。職場で Rust を書いている方が担当している領域がこれです。

今回の profile-site では、右側は自分では作りません。microCMS という他社のサービスを借りているので、「データを持っていて、頼めば返してくれる誰か」がすでに用意されている状態です。

用語の整理 クライアント＝頼む側。ブラウザ、スマホアプリなど。
サーバー＝答える側。ずっと起動していて、頼まれるのを待っている機械。
この2つは「役割の名前」であって、機械の種類ではありません。あなたの Mac も、プログラムを動かせばサーバーになります（bun run dev がまさにそれです）。

なぜ分かれているのか

データを1箇所に集めておかないと困るからです。あなたの Mac の中だけに記事データがあったら、他の人はそれを見られません。共有したいものは、常時起動している1箇所に置く。それがサーバーの存在理由です。

Chapter 2API = 他人のコンピュータの関数を呼ぶ

ここが一番の飛躍点なので、あなたが既に知っている概念に繋げます。

あなたはこう書いてきました。

const result = totalPrice(products);
//             ↑ 同じファイル、同じメモリの中にある関数

API とは、これを「別の機械にある関数」に対してやることです。

API（Application Programming Interface）とは、直訳すれば「プログラムから使うための窓口」です。microCMS は「この URL にこうやって頼めば、記事データを返します」という窓口を公開しています。

あなたが書いた src/lib/server/microcms.ts は、その窓口を、いつもの関数の見た目に包んだものです。

export const getWorks = (): Promise<Work[]> =>
    client.getAllContents<Work>({ endpoint: 'works', queries: { orders: 'order' } });

この Promise<Work[]> という戻り値の型が「時間がかかる」ことを表しています。次章以降で分解します。

演習 2-1

あなたがこれまで書いた関数のうち、「API に置き換えても呼び出し側の書き方がほとんど変わらないもの」を1つ挙げ、その理由を説明してください。

解答例を見る

たとえば問11 findByName(items, name)。呼び出し側は「名前を渡すと商品が1件返る（無ければ undefined）」としか知りません。中身が配列の .find でも、データベースへの問い合わせでも、呼び出し側の関心事は変わらないからです。

これがインターフェースという考え方です。「何を渡すと何が返るか」だけを約束し、中身を隠す。API の I はこの Interface です。

ただし1つだけ変わります。戻り値が Product | undefined から Promise<Product | undefined> になり、await が必要になる。「待つ」は隠しきれないのです。この点は第5章で扱います。

Chapter 3HTTP — 問い合わせの作法

「頼む」と言っても、相手は機械です。決まった形式でないと理解されません。その形式が HTTP です。

リクエスト（頼む側）に含まれるもの

要素意味今回の実例
URLどこの何が欲しいかhttps://xxx.microcms.io/api/v1/works
メソッド何をしたいかGET（取得したい）
ヘッダ付帯情報・身分証X-MICROCMS-API-KEY: xxxx
ボディ送るデータGET では使わない

メソッドは動詞だと思ってください。あなたが Lv5 でやった CRUD と対応します。

HTTP メソッド意味あなたが書いた対応物
GET取得問11 findByName
POST新規作成問39 addTodo
PUT / PATCH更新問37 toggleTodo
DELETE削除問38 removeTodo
重要な違い あなたの CRUD は不変更新でした（元を壊さず新しい配列を返す）。 一方サーバーの POST / DELETE は本当にデータを書き換えます。取り消せません。 だから GET 以外は慎重に扱います。今回のサイトは読むだけなので GET しか使いません。

レスポンス（答える側）— ステータスコード

返事の1行目には必ず3桁の番号が付きます。これは実際にあなたが今週遭遇したものです。

番号意味実際に起きたこと
200成功正しいキーで /works を叩いたとき
401認証されていないAPI キーを付けずに叩いたとき
404そんなものは無いworks をまだ作っていなかったとき
500サーバー側で異常が起きたキーの値に日本語が混じっていたとき

番号の先頭桁で大まかな分類ができます。

  • 2xx — 成功
  • 4xx — 頼み方が悪い（クライアントの責任）
  • 5xx — 相手側で壊れた（サーバーの責任）
デバッグの実際 この分類が切り分けの起点になります。4xx なら自分のコードを疑い、5xx なら相手を疑う。
実際、API キーの調査では「キー無し → 401」「でたらめなキー → 401」「実際のキー → 500」という差から、 「キーが間違っている」のではなく「キーの中身が異常」だと特定できました。 500 が返る＝相手のプログラムが処理しきれなかった、という意味だからです。

演習 3-1

あなたのサイトが公開された後、ブラウザで /works/存在しないID を開いたら何が起きるでしょうか。静的生成（prerender）していることを踏まえて考えてください。

解答例を見る

microCMS には一切問い合わせが行きません。 ビルド時に生成した HTML ファイルが並んでいるだけなので、存在しない URL は「ファイルが無い」＝ホスティング側が 404 を返して終わりです。

ここが静的生成の性質です。実行時にはサーバーのプログラムが動いていないので、動的な判断が一切できません。その代わり速く、壊れにくく、安い。

これは第6章の「コードがどこで動くか」に直結します。

Chapter 4JSON — 運ばれてくる形

ネットワークを通れるのは文字列（正確にはバイト列）だけです。TypeScript のオブジェクトをそのまま送ることはできません。

そこで、オブジェクトを文字列に変換する共通ルールが決められています。それが JSON です。

あなたの興味に直結する重要点

JSON.parse() の戻り値の型は any です。（unknown ですらありません）

つまり TypeScript の型検査を完全にすり抜けます。実際には { title: 123 } が来ているのに Work だと言い張っても、コンパイルは通ってしまう。

これがあなたのカリキュラム Lv7「境界の型付けと検証」で扱う穴そのものです。unknown に絞ってユーザー定義型ガードで検証する、という話は、まさにこの JSON の境界のためにあります。

今回 microcms-js-sdk を使っているのは、この面倒を SDK が肩代わりしてくれるからです。ただしSDK も実際には中身を検証していません。getWorks<Work>() の <Work> は「そう思って扱え」という指示であって、保証ではありません。

演習 4-1

microCMS 側で誰かが order フィールドを数字からテキストに変更したとします。あなたのコードはどうなるでしょうか。

解答例を見る

TypeScript は何も言いません。ビルドも通ります。 型は order?: number のままなので、コンパイラは「数値だ」と信じ続けます。

壊れるのは実行時です。たとえば a.order - b.order で並べ替えていたら NaN になり、並び順が静かに壊れる。エラーも出ずに間違った結果が出るのが最悪のパターンです。

これがあなたが強い関心を持っている「境界の検証」が必要な理由です。型注釈は自分との約束であって、外の世界とは無関係。外から来たデータは検証しない限り信用できません。

fail-loud の思想で言えば、「変な値が来たら派手に落ちる」ようにしておくべき箇所です。

Chapter 5なぜ「待つ」必要があるのか（非同期）

ここがあなたの Lv6 の内容です。先取りして基礎だけ押さえます。

問題設定

これまでのコードは上から順に、一瞬で実行されていました。

const a = totalPrice(products);  // 0.00001 秒
const b = a * 1.1;              // この時点で a は確実に入っている

しかし API 呼び出しは 0.1〜1秒 かかります。その間プログラムを止めてしまうと、ブラウザは固まります。

Promise — 「あとで値が入る箱」

あなたが Lv5 の問45 で扱っている RemoteData<T> を思い出してください。Promise はまさにあの考え方です。

// 問45 であなたが定義する型（4状態の判別可能ユニオン）
type RemoteData<T> =
    | { status: 'idle' }
    | { status: 'loading' }
    | { status: 'success'; data: T }
    | { status: 'failure'; error: string };

Promise<T> は、これを言語組み込みにしたものだと考えてください。

Promise の状態意味あなたの RemoteData
pendingまだ返事が来ていないloading
fulfilled値が入ったsuccess
rejected失敗したfailure
型の読み方 Promise<Work[]> は 「Work[] ではない」。「いつか Work[] になる箱」です。
だから .filter() を直接呼ぶことはできません。箱から出す操作が必要で、それが await です。

async / await

// ✘ 箱のまま。works は Promise なので filter は無い
const works = getWorks();
works.filter(...);   // 型エラー

// ✔ await で箱を開ける
const works = await getWorks();
works.filter(...);   // Work[] なので OK

ルールは2つだけです。

  1. await は async を付けた関数の中でしか書けない
  2. async を付けた関数の戻り値は自動的に Promise で包まれる
const load = async () => {          // ← async を付ける
    const works = await getWorks();   // ← だから await が書ける
    return { works };                // ← 実際の型は Promise<{ works: Work[] }>
};
よくある誤解 await は「プログラム全体を止める」のではありません。その関数の中の続きを、返事が来るまで保留するだけです。 他の処理は動き続けます。図4の下段がその様子です。

直列と並列

これは実務で必ず指摘される点なので、いま覚えてしまってください。

// 直列 — 遅い。works が終わってから posts を頼む
const works = await getWorks();   // 0.3秒
const posts = await getPosts();   // 0.3秒  → 合計 0.6秒

// 並列 — 速い。同時に頼んで、両方揃うのを待つ
const [works, posts] = await Promise.all([getWorks(), getPosts()]);
//                                                        → 合計 0.3秒

判断基準は「後の処理が前の結果に依存するか」です。依存しないなら並列にできます。依存するなら直列にせざるを得ません。

演習 5-1

次のコードは並列にできますか。理由も答えてください。

const ids = await getWorkIds();
const first = await getWork(ids[0]);
解答例を見る

できません。 getWork に渡す引数が getWorkIds の結果だからです。ID が分からないうちは2つ目を頼めません。依存関係があるものは直列にするしかないという典型例です。

補足として、ids[0] はあなたの tsconfig（noUncheckedIndexedAccess）だと string | undefined になります。これはあなたが「弱点4」として指導を受けた「undefinedが実際に湧く場所＝添字アクセス」そのものです。ガードが要ります。

Chapter 6コードはどこで動くのか

ここが SvelteKit で最も重要な概念です。 ファイル名の .server が何を意味するか、ここで分かります。

これまであなたが書いてきた .ts は、bun で実行する＝あなたの Mac の中だけで動いていました。ところが Web アプリでは、書いたコードが3つの異なる場所のどれかで動きます。

今回の構成で最も大事な一文 全ルートに prerender = true を指定しているので、+page.server.ts は bun run build を打った時に1回だけ実行され、結果が HTML に焼き込まれます。
公開後、閲覧者がページを開いても microCMS には一切問い合わせが行きません。

この性質から、いくつか実務的な帰結があります。

やりたいこと結果
console.log でデバッグ出力先はビルドを打ったターミナル。ブラウザのコンソールではない
記事を更新して反映再ビルドが必要（だから Webhook で自動ビルドを仕込む）
アクセスした人ごとに違う内容を出すできない。全員が同じ HTML を見る
表示速度非常に速い。ファイルを返すだけ

演習 6-1

なぜ +page.ts（.server なし）には API キーを書いてはいけないのでしょうか。図5を見ながら説明してください。

解答例を見る

+page.ts はブラウザでも動くからです。ブラウザで動くということは、そのコードが閲覧者の PC にダウンロードされるということ。つまり誰でも中身を読めます。

実際 SvelteKit は、+page.ts から $env/static/private を import するとビルドを失敗させます。うっかりでは漏らせない仕組みになっています。

これは $lib/server/ ディレクトリも同じで、クライアント側から import した瞬間にビルドが落ちます。規約ではなく仕組みで守られている境界は貴重なので、API キーに触るコードは必ずここに置きます。

Chapter 7なぜ API キーをサーバーに置くのか

ここは短く、しかし決定的に重要です。

ブラウザに送られたコードは、全部読めます。 難読化しても、圧縮しても、読めます。開発者ツールを開けば誰でも見られる。

// もしブラウザで動くコードにこう書いたら
const key = 'abc123...';   // ← 世界中に公開しているのと同じ

API キーが漏れると、第三者があなたの microCMS に対して自由に読み書きできます。記事の削除も可能です。

今回の構成が安全な理由
  1. キーは .env に書いてある（.gitignore 済み）
  2. 読むのは $lib/server/microcms.ts だけ
  3. そこは +page.server.ts からしか呼ばれない
  4. それはビルド時にしか動かない
  5. 結果、キーは生成された HTML のどこにも含まれない

この5段の連鎖が、あなたが作った構成です。1つでも崩れると漏れます。

Chapter 8load / entries / $types

ここまでの土台の上で、ようやく本題です。3つしかありません。

load — データを取ってきて渡す

SvelteKit との約束は「load という名前で export した関数の戻り値が、画面に data として届く」だけです。

// +page.server.ts
export const load = async () => {
    const works = await getWorks();
    return { works };        // ← このオブジェクトが data になる
};
// +page.svelte
let { data } = $props();
data.works                     // ← 上で return した works が入っている
なぜ「返す」だけで届くのか これは SvelteKit が決めた規約です。フォルダ名・ファイル名・export 名の組み合わせで フレームワークが自動的に繋いでくれます。あなたが import して呼び出すわけではありません。
「規約に従うと勝手に動く」のがフレームワークの正体です。慣れるまで気持ち悪いですが、 覚えるべきルールが減るという利点があります。

entries — どのページを作るか列挙する

これは [id] が付いた動的ルートだけに必要です。

静的生成では、ビルド時に全ページを作りきる必要があります。ところが /works/[id] の [id] には無限の可能性があるので、SvelteKit は何を作ればいいか分かりません。それを教えるのが entries です。

export const entries = async () => {
    const ids = await getWorkIds();   // ['profile-site']
    return ids.map((id) => ({ id }));   // [{ id: 'profile-site' }]
};

この .map は、あなたが問4から使っているものと完全に同じです。文字列の配列を、オブジェクトの配列に変換しているだけ。

返した数だけページが生成されます。

$types — 自動生成される型

./$types という不思議な import 元は、SvelteKit がフォルダ構成から自動生成した型です。手で書きません。

// .svelte-kit/types/.../works/[id]/$types.d.ts に自動生成されている
type RouteParams = { id: string };

[id] というフォルダ名から { id: string } が導出されています。 だから params.id に型が付き、params.slug と書き間違えるとコンパイルエラーになる。

フォルダ名を [slug] に変えれば、型も自動的に { slug: string } に変わります。ファイル構成が型の源になっている、というのがこの仕組みの面白いところです。

演習 8-1

一覧ページ /works（works/+page.server.ts）に entries は必要でしょうか。

解答例を見る

不要です。 URL が /works で固定されており、[id] のような可変部分がないからです。作るページは1枚だけなので、列挙する必要がありません。

言い換えると、entries が必要なのは「フォルダ名に [] が含まれるルート」だけです。

演習 8-2

load の中で await を書き忘れて return { works: getWorks() } としたら、+page.svelte の data.works には何が入るでしょうか。

解答例を見る

Promise（＝まだ中身の入っていない箱）が入ります。 当然 .map も .length も使えません。

型で言えば Work[] ではなく Promise<Work[]> です。これは第5章の「Promise<T> は T ではない」がそのまま効く場面です。

なお SvelteKit には Promise をそのまま返して段階的に表示する機能（ストリーミング）もありますが、静的生成では使えません。HTML を作りきるには全部揃っている必要があるからです。今回は必ず await してください。

Chapter 9全体を1枚で

まとめ — 覚えるべきこと

概念一言でいうと
サーバー / クライアント頼む側と答える側。物理的に別の機械
API他人のコンピュータの関数を呼ぶ窓口
HTTPその頼み方の作法。ステータスコードで結果が分かる
JSON運ぶための文字列形式。ここで型が消える
Promiseあとで値が入る箱。あなたの RemoteData と同じ発想
async / await箱を開けるための構文
.server「ブラウザに送らない」という宣言。秘密を置ける場所
prerenderビルド時に全部作る。実行時にサーバーは動かない
load返した値が data として画面に届く規約
entries動的ルートで「どのページを作るか」を列挙する
あなたのカリキュラムとの接続

Lv6（問46〜50）非同期と境界 — 第5章がその内容そのものです。Promise / async / await / fetch / エラー処理。今回のコードは Lv6 の実物版です。

Lv7（問51〜58）境界の型付けと検証 — 第4章の「JSON で型が消える」がその動機です。unknown に絞る、ユーザー定義型ガードを書く、Result で fail-loud にする。API から返ってきた JSON こそが「信用できない外部データ」の代表例です。

つまり今回のプロジェクトは、あなたがこれから学ぶ内容の実地の題材になっています。Lv6・Lv7 を進めるとき、抽象的な toy 問題ではなく「あの profile-site のあの箇所」として思い出せるはずです。
