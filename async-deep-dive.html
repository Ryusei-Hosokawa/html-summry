問46はなにをする課題か（全体像）

ひとことで言うと、問46は 「本番のデータ取得」のごっこ遊び です。 本番には存在する「サーバー」と「通信にかかる時間」を、手元で偽物として用意し、 あらゆるデータ取得に共通する“形”だけを練習します。

課題は2つ。delay（時間がかかる処理の偽物を、自分の手で作る）と、 fetchTitle（その偽物を使って「idを渡すとタイトルが返ってくる」偽のAPIを組む）。 下の図が問46の全景です。

この資料のゴール

「道具の動き」だけでなく 「なぜそれが要るのか／なにが嬉しいのか」 まで腑に落とすこと。 次の章から、箱（Promise）の正体 → 作り方 → 使い方 → 本番（fetch）との繋がり、の順で積み上げます。

2

Promiseとは ― 未来の値が入る「箱」

Promiseは「いつか値が入る箱」です。フードコートの呼び出しベルを思い浮かべてください。 ラーメンを注文しても、すぐには出てこない。店員が渡してくるのはベルです。 このベルはラーメンそのものではなく、「そのうちラーメンが来る」という引換券。これがPromiseです。

だから Promise<string> は string ではありません。 「そのうち string が入るベル」です。ベルを直接 console.log すると [object Promise] と出るのは、「ラーメンではなくベルを表示してしまった」状態。

ベルには3つの状態があります。この3状態は、問45で作った RemoteData とほぼ同じ形です。

覚えるのはこれだけ

Promise＝「あとで中身が入るベル」。今はまだ中身が無いから、ベル（箱）を先に受け取っておく。

3

なぜPromiseが必要か ― 固まらせない

JavaScriptは一度に1つのことしかできません（シングルスレッド）。 もし「サーバーからデータが来るまで待つ」を素直に書いて500ミリ秒止まると、その間 ページ全体が凍りつきます ― スクロールもクリックも、ローディングのくるくるすら止まる。

だから「ただ待つ」は選べない。かといって「まだ無い値」を今すぐ返すこともできない。 この板挟みの答えがPromiseです。値そのものは今渡せないけれど、 「あとで届くよ」というベルを今渡す。あなたはベルを持って別の作業に移れる＝ページは固まりません。

しかも選択の余地もありません。いまのWeb開発で「時間がかかること」は、 すべてPromiseで返ってきます。

サーバー通信

fetch() でデータを取る

ファイル読込

FileReader で読む

一定時間待つ

つまり

Promiseは「知っておくと便利」ではなく、これ無しでは何もデータを取ってこれない土台です。

4

new Promise ― 箱を「作る側」に立つ

普段はベル（Promise）を fetch が作ってくれます。お題1は逆に、 一度だけベルを自分の手で作って、仕組みを覗く練習です。それが delay。

const delay = (ms: number): Promise<void> =>
  new Promise((resolve) => {
    setTimeout(resolve, ms)
  })

読み解くコツは「箱の内と外」です。呼び出し元に手渡すのはベル（Promise）なので、 一番外側は必ず new Promise。setTimeout はその内側に住む 「目覚まし時計」にすぎません。

よくある逆転ミス

setTimeout(new Promise(), ms) と書くと内と外が反対。 setTimeout が返すのはタイマーID（数値）で、Promiseではないので型が合いません。 「returnする一番外側の型はPromiseか？」と自問すると気づけます。

5

resolveの正体 ― 箱を確定させるボタン

resolve は、Promiseが「はい、これ使って」と渡してくる関数です。 あなたが作るのではなく受け取るもの。これがLv4の高階関数と同じ構造 ― .map(x => ...) で配列があなたの関数に x を渡したのと同じで、 今回は new Promise があなたの関数に resolve を渡します。

resolve(値) と値を渡すと、その値が箱の中身になり、 await した側がその値を受け取ります。delay は中身が無い void なので resolve()（合図だけ）。

なぜ resolve() ではなく resolve を渡すのか

setTimeout(resolve, ms) は「関数そのものを渡す」。押すのはsetTimeout（ms後）。 resolve() と書くと今すぐ自分で押してしまい、待つ意味が消えます。 問36の eta変換（x => f(x) と f の違い）と同じ論点です。

6

await ― 箱を開けて待つ

await ベル は「このベルが鳴るまで待つ→ 鳴ったら中身をちょうだい」。 待っている間もページは固まりません（章3）。

const title = await fetchTitle(1)   // 届くまで待って、届いたら title に入る
console.log(title)                  // この行は "その後" に動く

await 忘れ＝実務バグ第1位

忘れると「ベルそのもの」が流れて [object Promise] に。 箱は常に truthy なので if も素通りしがち。「時間がかかる関数を呼んだら await」を癖に。

7

async ― 箱を自動で作ってくれる

関数に async を付けると、その関数は返り値を自動でPromiseに包みます。 だからお題2では自分で new Promise を書きません。中では 「待ちたいものを await して、最後に値を return するだけ」。

const fetchTitle = async (id: number): Promise<string> => {
  await delay(100)
  // ... TITLES[id] を引く ...
  return title   // ← 裏で resolve(title) しているのと同じ
}

お題1: delay

あなたがベル職人。new Promise で手作り。 resolveを自分で仕掛ける。

お題2: fetchTitle

async がベルを自動生成。 return 値 がresolveの代わり。

async と new Promise の関係

箱の作り方は2通りあって、どちらか一方を選ぶ。 async 関数の中で new Promise を書くのは二重で不要。 return x が、章5の resolve(x) を自動で押しているのと同じです。

8

fetchとは ＆ delayとの関係

fetch はブラウザに最初から入っている 「サーバーにデータを取りに行く」関数です。URLを渡すと相手に問い合わせ、返事を持って帰る。

const res = await fetch('https://example.com/api/titles/1')
const data = await res.json()   // 返事の本文を取り出す（これも待つ）

問い合わせは時間がかかるので、fetch はデータではなく 「あとで返事が入るベル」＝Promiseを即座に返します。ここが delay と全く同じ構造。 両方Promiseで、違うのは「いつベルが鳴るか（トリガー）」だけです。

await delay(100)              // 100ms待つ
const res = await fetch(url)  // 返事が来るまで待つ ← 形がそっくり

だから問46でdelayを使う

練習にはサーバーが無いので、fetchの「時間がかかる」性質だけを delay(100) で再現しています。 fetchTitle の中の await delay(100) は、本番の await fetch(...) の予行演習。同じ扱い方なので、そのまま本物に移せます。

9

お題2 fetchTitle の目的

fetchTitle は、将来書く fetch(...) の替え玉です。 通信の面倒（URL・設定・エラー）を抜きに、「待つ→受け取る→返す」という“形”だけを裸で練習できます。

やりたいこと（道具を抜いた日本語）

1  id を受け取る

2  delay(100) を await で待つ（通信のふり）

3  TITLES[id] を引く

4  あれば返す／無ければ「見つからない」をどう表すか自分で決める

手元の“偽物”は、本番のなにを演じているか

delay(100)
→
通信のタイムラグ（サーバーが考える時間）
TITLES = {…}
→
バックエンドのDB
fetchTitle(id)
→
fetch('/api/titles/' + id)
見つからない時の設計
→
404・通信エラーの処理（→ 問49 Result型）

ここが答え合わせの主役

「見つからない id をどう扱うか（throw / 別の型 / その他）」＋その理由。 正解は1つではありません。noUncheckedIndexedAccess により TITLES[id] は string | undefined ―― この undefined の扱いが設計判断です。

全体像 ― RemoteDataと組んで実画面に

「なにが嬉しいのか」の最終回答がこれです。fetchTitle が書ければ あらゆるデータ取得が書けるようになり、問45の RemoteData と組み合わせると、 そのまま「読み込み中 → 表示 or エラー」の実画面1つになります。

いま作っているものの正体

Reactのデータ取得は全部これ。「APIから取って画面に出す」の全てが Promise ＋ async/await ＋（loadingの）状態管理。 問46は、Reactアプリで一番よく使う血管そのものを組む練習です。
