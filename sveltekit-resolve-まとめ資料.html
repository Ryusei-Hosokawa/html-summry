resolve() と「定数によるパス管理」
なぜ生の文字列連結ではダメなのか

HTMLコーディングの感覚で書く "/products/" + id のような文字列連結には、実は3つの見えない事故リスクがあります。この資料では、その正体と resolve() がどう解決するかを、図とデモで体験しながら理解します。

結論（TL;DR） resolve()とは リスク1: base path リスク2: 型安全 リスク3: リネーム 定数管理との両立 比較まとめ

ひとことで言うと

文字列連結は URL を「人間が手で当て推量」して組み立てている。
resolve() は URL を「ルート定義から導出」する。
だから base path・パラメータの過不足・フォルダのリネームのズレを、実行前（ビルド時）に検出できる。

0

resolve() とは何か

$app/paths が提供する、URL（パス）を正しく組み立てるための関数です。使い方は2通り。 

import { resolve } from '$app/paths';

// (a) 静的なパスを解決（base path を前置するだけ）
resolve('/blog/hello-world');

// (b) ルートID + パラメータで動的パスを組み立てる
resolve('/blog/[slug]', { slug: 'hello-world' });

(b) の第1引数「ルートID」は、src/routes/ の実際のフォルダ構造と完全に一致していなければなりません。[slug] という名前もフォルダ名と一致が必須です。この「実構造との一致」こそが、後述の型安全とリネーム検出の土台になります。

1

配信環境が変わるとリンクが全部壊れる

RISK — base path

文字列連結 "/products/" + id は「サイトがドメイン直下で動く」前提。もしアプリを https://example.com/admin/ のようなサブディレクトリ配下で配信すると、正しい URL は /admin/... なのに /admin が抜け落ち、全リンクが404になります。

resolve() 常に正しい

ボタンを切り替えると、base path 導入時に文字列連結だけがズレるのが分かります。

2

パラメータのミスを誰もチェックしてくれない

RISK — 型安全

TypeScript から見れば、文字列連結は「ただの文字列 + 文字列」。中身が正しい URL かは一切検査されません。だから次のミスが警告ゼロで素通りし、実行して初めて壊れます。

✕ 文字列連結（検査なし）
// productId を付け忘れ
goto(PATH.PRODUCTS + '/' + categoryId + '/edit/');
// → TS的には正しい文字列。
//   警告ゼロ・実行して初めて気づく
✓ resolve()（型で検査）
// 必要なパラメータが型で分かる
resolve(ID.PRODUCT_EDIT, { categoryId });
// → productId が無い！
// コンパイルエラーで即発覚

ルート /products/[categoryId]/edit/[productId] に渡すパラメータを、チップをクリックして出し入れしてみてください。

categoryId productId
3

フォルダ名を変えたときに気づけない

RISK — リネーム耐性

SvelteKit は「フォルダ構造 = URL」。将来 products/ を items/ にリネームすると…

4

「定数で一元管理」は捨てなくていい

コツは、定数に持たせる値を「連結済みの生パス」ではなく「ルートIDのテンプレート」にすること。管理の一元化はそのまま、SvelteKit作法とも両立します。

① ルートIDを定数化（as const が必須）

// consts/routeId.ts — ディレクトリ構造と一致させる
export const ROUTE_ID = {
  PRODUCT_LIST: '/products/[categoryId]',
  PRODUCT_EDIT: '/products/[categoryId]/edit/[productId]'
} as const; // ← これが無いと型が string に広がり resolve() で型エラー

② 呼び出し側

import { resolve } from '$app/paths';
import { ROUTE_ID } from '@/consts/routeId';

// 一覧へ
goto(resolve(ROUTE_ID.PRODUCT_LIST, { categoryId }));

// 編集へ（パラメータ不足はコンパイルエラーになる）
goto(resolve(ROUTE_ID.PRODUCT_EDIT, { categoryId, productId }));

なぜ as const が要るか：resolve() は「実在するルートIDのリテラル型の一覧」で型付けされています。as const が無いと定数の型がただの string に広がってしまい、「特定のルートID」という厳密な型に一致せず型エラーになります。as const でリテラル型に固定することで一致します。

5

比較まとめ

観点 文字列連結（生パス） resolve() + ルートID定数
base path 対応 ✕ 付け忘れて404 ○ 自動で前置
パラメータ検査 ✕ 過不足・順序ミスが素通り ○ 型で強制・コンパイル検出
フォルダのリネーム ✕ 実行するまで気づけない ○ ビルド時に全件エラー
定数での一元管理 ○ 可能（ただし"推測値"） ○ 可能（実構造に由来）
lint 警告 ✕ no-navigation-without-resolve ○ 解消

チーム導入の現実解：ルートIDの型付けは版依存の癖があるため、全 goto を一斉置換せず、新規・改修箇所から段階導入し、ROUTE_ID 定数を新設して既存の生パス定数と併存させながら移行するのが安全です。
